Коротко: “синхронизация” в OpenCity — это не один протокол, а связка из трёх слоёв: **идентичность → транспорт → данные**. Ниже — минимальный, реальный к внедрению стек (MVP) и как им пользуются «жители».

# Базовый стек OpenCity (MVP)

1) **Идентичность и доверие**  
- **DID** (децентрализованные идентификаторы) для жителей и агентов.  
- **Verifiable Credentials** (атрибуты: роль, районы, права).  
- **Подписи / E2E-шифрование**: на уровне комнат и документов (Olm/Megolm как в Matrix или DIDComm v2).

2) **Транспорт и доставляемость**  
- **Matrix** как шина событий в реальном времени (комнаты = районы/проекты).  
- **libp2p** для p2p-сессий (локальная синхронизация, оффлайн-мосты, gossip).  
- **IPFS/Content-Addressed Storage** для больших артефактов (медиа, бандлы данных).

3) **Данные и разрешение конфликтов**  
- **CRDT-документы** (Automerge/Yjs) для совместного редактирования без «замков».  
- **Меркл-DAG/хеш-цепочки** для истории и проверяемости.  
- **Событийная модель (event-sourcing)**: всё — события; состояния — производные.

> Лозунг «Люди больше не спорят — они синхронизируются» реализуется CRDT-уровнем: любые параллельные правки сходятся детерминированно, без ручных «merge-адов».

---

# Как это выглядит для жителя

### Режимы синхронизации
- **Real-time**: Matrix-комната + CRDT-док ~ «совместная карта района»/«канва проекта».  
- **Оффлайн-first**: правишь локально → при появлении сети libp2p gossip разносит дельты → Matrix подтверждает и рассылает.  
- **Асинхронно-ритуальный**: решения фиксируются как подписанные события (решение/голос/мандат) → попадают в общий «городской реестр» (меркл-журнал).

### Уровни синхронизации
- **L0: Presence** — кто онлайн/рядом (BLE/Wi-Fi-Direct, mDNS), статус/намерение.  
- **L1: State** — общие доски, документы, карты (CRDT).  
- **L2: Intent** — заявки/предложения в унифицированном формате (см. ниже).  
- **L3: Decision** — зафиксированные решения с подписями + правила исполнения.

# Мини-спецификация сообщений (черновик)

### 1) Событие (общий каркас)
```json
{
  "v": "1.0",
  "type": "city.event",
  "subtype": "proposal|vote|grant|comment|patch",
  "id": "hash(base64)",
  "topic": "district:central:cleanup-2025-11-10",
  "issued_at": "2025-11-04T09:21:13Z",
  "actor_did": "did:key:z6Mkh...",
  "payload_cid": "bafy... (опционально)",
  "crdt_delta": { /* если это правка общего документа */ },
  "sig": "ed25519..."
}
```

### 2) Предложение (Intent)
```json
{
  "type": "city.event",
  "subtype": "proposal",
  "proposal": {
    "title": "Субботник во дворе",
    "time_window": ["2025-11-10T09:00Z","2025-11-10T12:00Z"],
    "resources": ["мешки", "перчатки"],
    "needs": ["10 волонтёров"],
    "location": "geo:60.1699,24.9384",
    "tags": ["eco","community"]
  }
}
```

### 3) Голос/одобрение (Decision input)
```json
{
  "type": "city.event",
  "subtype": "vote",
  "ref": "hash(proposal)",
  "vote": { "choice": "yes", "weight": 1, "reason": "иду" }
}
```

### 4) Патч общего состояния района (CRDT)
```json
{
  "type": "city.event",
  "subtype": "patch",
  "doc_id": "district:central:board",
  "crdt_delta": { "...": "..." }
}
```

# Правила сходимости и споров (без споров 😄)

- **CRDT-правки** всегда коммутативны → общий документ «сходится».  
- **Нормативные коллизии** (кто «имеет право»): решаются **правами из VC** + политиками комнаты/проекта (роли: житель, модератор, координатор).  
- **Решения** фиксируются как набор подписанных событий; «итог» считается по заранее выбранной процедуре (кворум/взвешивание/делегирование).  
- **Аудит**: любой итог пересчитываем из журнала событий (меркл-претрассируемость).

---

# Безопасность и приватность

- **E2E-комнаты** для чувствительных тем; публичные — с проверяемыми подписями.  
- **Разделение контуров**: публичный городской слой / приватные кооперативы / персональные агенты.  
- **Разрешения на дельты**: даже CRDT-патчи проходят валидацию политик.

---

# Почему такой протокол-стек

- **Практичен сейчас**: Matrix + Automerge/Yjs + DID/VC + libp2p/IPFS — зрелые кирпичи.  
- **Оффлайн-first по умолчанию**: жители не зависят от «единого центра».  
- **Проверяемость**: решения и история действий не «теряются» и не переписываются задним числом.  
- **Расширяемость**: легко добавить ActivityPub-мосты, NATS/Redpanda как backbone, геослои, микросервисы агентов.

---

# Что можно сделать уже сегодня

5) Провести пилот «субботник/ярмарка»: реальное голосование → план работ → протокол выполнения.

### 🧠 Что значит «синхронизироваться»

В Городе Нейросеть люди не спорят, кто прав.  
Они **синхронизируются** — то есть приводят свои взгляды, действия и данные в общее состояние.  
Это не магия, а новая форма общения: не через слова, а через **совместное состояние**.

---

### ⚙️ Как это выглядит изнутри (в жизни жителя)

1. **У каждого жителя есть свой личный “агент”** — как умный секретарь.  
   Он знает твои цели, привычки, проекты и помогает согласовывать их с другими.  
   Например, если ты планируешь мероприятие — агент сразу показывает, кто рядом уже делает что-то похожее.

2. **Все жители связаны не сетью сообщений, а сетью смыслов.**  
   Когда ты предлагаешь идею («пора убрать двор»), это не сообщение в чат,  
   а **новая точка в общей карте города**, куда могут подключиться другие — с помощью своих агентов.

3. **Синхронизация происходит мягко, без конфликтов.**  
   Если кто-то вносит изменения, система не спорит, чья версия правильнее.  
   Она просто объединяет всё в единую картину — как если бы город сам “примирял” мнения жителей.

4. **Каждое решение фиксируется честно и прозрачно.**  
   Не как пост в чате, а как факт: “Жители согласовали субботник на 10 ноября”.  
   Эти факты нельзя удалить, но можно переосмыслить — и город «поймёт» обновление.

5. **Даже офлайн всё работает.**  
   Если кто-то был без сети, его изменения позже подхватываются,  
   и общий порядок сам восстанавливается, как будто “всё время шло правильно”.

### 🌐 На каком «протоколе» это всё держится

Если говорить совсем просто —  
**на протоколе доверия, контекста и согласия**:

| Слой | Что это значит |
|------|----------------|
